# buildcard

Информация о сборке и запущенном Go-приложении. Только стандартная библиотека, Go 1.25 или новее.

## Установка

После публикации этих изменений в `github.com/LittleDrongo/buildcard`:

```sh
go get github.com/LittleDrongo/buildcard@latest
```

Пакет находится в корне модуля; импортировать вложенный путь `/buildcard` не нужно.

```go
package main

import (
    "github.com/LittleDrongo/buildcard"
)

func main() {
    info := buildcard.Snapshot()
    info.Preview()
}
```

Пример в репозитории: `go run ./sample`.

## API

- `Info` — все данные снимка в открытых полях: версия, коммит, даты, признак изменений, репозиторий и окружение процесса. Например, `info.Version` и `info.CommitHash`.
- `Snapshot() Info` — возвращает экземпляр структуры со снимком метаданных и окружения процесса: ОС, архитектура, пользователь, имя машины, путь программы, PID и аргументы после имени бинарного файла. Время работы отсчитывается от инициализации пакета.
- `info.Preview()` — выводит таблицу в stdout. Показывает сохранённый снимок; для обновления данных снова вызовите `Snapshot()`.
- `info.String()` — снимок в виде таблицы для логов.
- `info.WriteTable(io.Writer)` — таблица снимка в выбранный поток с возвратом ошибки записи.
- При необходимости `Info` можно сериализовать стандартным `json.Marshal(info)`: имена ключей совпадают с именами полей структуры.

Импорт сам по себе ничего не печатает. Таблицы используют русские подписи и локальный часовой пояс. Снимок содержит имя пользователя, машины и аргументы запуска — учитывайте это при выборе данных для публичного вывода.

## Метаданные сборки

По умолчанию пакет читает `runtime/debug.ReadBuildInfo`: версию и путь **главного модуля приложения**, а также `vcs.revision`, `vcs.time`, `vcs.modified`, если Go включил их в бинарный файл. Версия зависимости `buildcard` не используется как версия приложения.

Если `buildRepository` не задан, при запуске из исходников пакет ищет ближайший `go.mod` от текущего каталога вверх. Если имя модуля совпадает с главным модулем исполняемого файла, поле `Repository` берётся из локального `remote.origin.url`. Например, модуль `emal_processing` может показывать `git@gitlab.services.mts.ru:clr_group_msk/email_invoice_stamp_cleaner.git`. Git вызывается только для чтения локальной настройки, без сети, с таймаутом в одну секунду. Без Git, подходящего исходного дерева или `origin` остаётся путь Go-модуля. Из URL удаляются учётные данные, query и fragment; SSH-адреса вида `git@host:group/repo.git` сохраняются.

В Docker без исходников и Git URL репозитория нужно передавать при сборке через `buildRepository`. Явное значение имеет приоритет, включая значения, переданные внешней утилитой сборки. Если deployctl передаёт туда имя модуля, необходимо обновить и логику сборки deployctl — библиотека не может восстановить отсутствующий URL из готового бинарника.

Пользователь определяется по системной записи, затем по переменным `USER`, `LOGNAME`, `USERNAME`. В Linux-контейнере с числовым UID без записи в `/etc/passwd` и без этих переменных выводится, например, `uid=789010`, а не `unknown`. Имя пользователя хоста по одному UID восстановить нельзя; для отображения имени передайте `USER` в окружении контейнера. Это информационное значение и оно не изменяет права процесса.

В локальной сборке версия обычно `DEV`. Если VCS-данные не встроены (например, сборка вне Git или с `-buildvcs=false`), коммит будет `unknown`. Go не предоставляет дату сборки: без явного значения поле `info.BuildTime` содержит `unknown`. Даты снимка представлены строками RFC3339 в локальном часовом поясе; недоступные даты — строкой `unknown`.

Переопределения через `-ldflags` имеют приоритет:

```sh
go build -ldflags="-X github.com/LittleDrongo/buildcard.buildVersion=v1.0.0 -X github.com/LittleDrongo/buildcard.buildTime=2026-09-14T12:00:00Z" .
```

Команда выполняется в проекте приложения. Для примера из этого репозитория замените `.` на `./sample`.

| Переменная после `github.com/LittleDrongo/buildcard.` | Значение |
| --- | --- |
| `buildVersion` | Версия приложения |
| `buildCommitHash` | Полный хеш коммита |
| `buildCommitShort` | Короткий хеш; по умолчанию первые 7 символов полного |
| `buildCommitDate` | Дата коммита в RFC3339 или Unix seconds |
| `buildDirty` | `true` или `false` |
| `buildTime` | Дата сборки в RFC3339 или Unix seconds |
| `buildRepository` | URL репозитория; по умолчанию путь главного модуля |

## Информация о контейнере

`Snapshot()` заполняет дополнительные поля `Info`; `String()`, `Preview()` и `WriteTable()` отображают их из сохранённого снимка:

| Поле | Смысл | Переменная окружения |
| --- | --- | --- |
| `InContainer` | Приложение запущено в контейнере | `BUILDCARD_CONTAINER=true` |
| `ContainerHost` | Хост контейнерного движка | `BUILDCARD_CONTAINER_HOST` |
| `ContainerUser` | Пользователь, запустивший деплой | `BUILDCARD_CONTAINER_USER` |
| `ContainerName` | Имя контейнера | `BUILDCARD_CONTAINER_NAME` |
| `ContainerImage` | Образ, например `service:v1.2.3` | `BUILDCARD_CONTAINER_IMAGE` |

Без явного флага на Linux проверяются `/.dockerenv` и `/run/.containerenv`. Это эвристика, а не гарантия обнаружения любого контейнера. Для других окружений передайте `BUILDCARD_CONTAINER=true`; значение `false` явно отключает определение. Вне контейнера все новые поля имеют zero value: `false` и `""`, даже если переменные с описанием контейнера присутствуют. В таблице пустые значения остаются пустыми.

Хост движка и пользователь запуска не выводятся из hostname и UID приложения: эти данные передаёт система запуска. Обновлённый deployctl передаёт все пять переменных автоматически, используя имя Docker daemon и имя SSH-пользователя, выполняющего деплой. Внешние средства запуска могут передать их через `docker run --env`. Без переданных данных контейнер определяется, но неизвестные поля остаются пустыми. Значения информационные, не предназначены для проверки прав доступа.

`Hostname` и `Username` по-прежнему описывают процесс внутри контейнера. Методы вывода не обновляют снимок — для свежих данных вызовите `Snapshot()` снова.

## Проверка и публикация

```sh
go test ./...
go vet ./...
```

Для установки через `go get` изменения должны быть опубликованы в доступном пользователям GitHub-репозитории. Для версионированного релиза создайте и отправьте тег, например `v0.1.0`; после этого пользователи смогут выполнить `go get github.com/LittleDrongo/buildcard@v0.1.0`.
